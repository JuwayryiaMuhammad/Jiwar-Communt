# Dashboards

Two Next.js 16 dashboards for this backend, in the same pnpm workspace (`pnpm-workspace.yaml` at the repo root):

| App | Port | Who | Sign-in |
|---|---|---|---|
| `apps/admin` | 3001 | Platform super admin | Email + password (`/platform/auth/*`), forced password change on first sign-in |
| `apps/manager` | 3002 | Compound manager, maintenance supervisor | Email or phone → 6-digit code by email → pick the account. Admitted: managers, and any role holding one of the entry permissions (`ENTRY_PERMISSIONS` in `apps/manager/lib/access.ts`, read from `GET /me` at sign-in); anyone else is signed out at once and shown "No access" |

Both follow the design system in `docs/decisions/DESIGN.md`. The tokens live in `packages/ui/src/styles.css`.

```
apps/admin        super admin: compounds, managers, security events, platform audit, account
apps/manager      manager: overview, requests, units, residents, workers, maintenance, gate, parcels, partners, staff, accounts, roles, settings, maintenance setup, deletion requests, audit, notifications, own account
apps/public       the public web pages the API's links open (port 3003); not a dashboard, see apps/public/README.md
apps/Dockerfile   one image per app (--build-arg APP=admin|manager|public), Next.js standalone output
packages/ui       design tokens + components (shell, cards, tables, dialogs, forms, toasts)
packages/api      types generated from docs/api/openapi.v0.json, typed client, error texts, React data hooks
packages/bff      server-only: cookie session, /bff proxy, single-flight token refresh, CSRF guard
```

## Run

With Docker, `docker compose up -d --build` at the repo root starts the API and both dashboards (root README).

On the host, against an API on the host or in Docker:

```bash
pnpm install                                         # at the repo root, once
cp apps/admin/.env.example apps/admin/.env.local     # JIWAR_API_URL, e.g. http://localhost:3100
cp apps/manager/.env.example apps/manager/.env.local
pnpm dev:admin       # http://localhost:3001
pnpm dev:manager     # http://localhost:3002
```

`JIWAR_API_URL` is the API origin without `/api/v1`, read on the server only.

After an API change (`pnpm openapi:export`), regenerate the client types; CI fails while they are stale:

```bash
pnpm api:generate
pnpm dashboards:typecheck
```

## How the dashboards talk to the API (BFF)

The browser never holds a token and never calls the API. Each app has a backend-for-frontend under `/bff`:

- `/bff/auth/*`: sign-in, sign-out and session routes. Tokens go into httpOnly cookies: the access token and refresh token are scoped to `/bff`, and a secret-free marker cookie on `/` lets `proxy.ts` send signed-out visitors to `/login`.
- `/bff/api/v1/...`: forwards an allow-listed call with `Authorization: Bearer`. The admin app forwards `/api/v1/platform/*` only (not `platform/auth`). The manager app forwards everything except `platform`, `auth`, `public` and the public invite and registration flows. A path with `.` or `..` segments gets 404. Error bodies are passed through without the API's developer `message` and `path`.
- **Refresh.** The API rotates refresh tokens and revokes the session when a rotated token comes back (reuse detection, ADR 0004). The BFF therefore refreshes each token once (single flight). For 30 s afterwards it hands the same result to late requests that still carry the old cookie. A 401 is retried once after a refresh; the auth guard rejects before any handler runs, so the retry cannot repeat a side effect. The refresh state is per process, so run one BFF instance per app or use sticky sessions.
- **CSRF.** Every `/bff` call must carry `x-jiwar-bff: 1`, a custom header that forces a CORS preflight the BFF never answers. Non-GET calls must come from the same `Origin`. Cookies are `SameSite=Lax`, or `Strict` for the login ticket.

Because of the BFF, the API needs no `CORS_ORIGINS` for the dashboards.

## Permissions

`GET /me` returns the role's permissions. The shell shows a section only to a role that may read it, and asks for a queue's count only then (`lib/permissions.tsx`: `usePermissions`, `Can`). This is for showing and hiding; the API decides every call, and a 403 renders as "No access" where it lands.

## Known limits (API v0)

- Pickers (ADR 0072): units, residents, accounts, assets and vendors list the first 50 and find any other by what is typed, which the API searches (`q`: part of a code or a name, for people also the exact phone or email); the chosen one stays in view and the field says when more match than are listed. A ticket opened for a resident in a common area finds its reporter that way (for a unit, the API lists who may report there).
- The reinforcement call starts a number of hours from now (a quarter of an hour to twelve ahead, as the API takes it) and names a zone or the whole compound; a roster's single slot names one too.
- A technician's location is read one technician at a time, when picked or "Read again" is pressed (every read is audited, and none happens on a window's focus), and drawn as a plot of that one point with rings, north and its accuracy. No map tiles or keys are loaded, and several technicians' locations are never shown together or read in one call; the coordinates open a public map in a new tab.

- The overview's numbers come from the dashboard's summary (ADR 0079), counted in the database; the sidebar's badges read one page of up to 100 rows and show `99+` beyond that, and the dispatch setup counts its waiting queue by following the pages up to 1000 (`1000+` past that).
- The unit register (ADR 0072): Units searches by part of the code, and the manager (`units.manage`) filters by building and status, downloads the CSV, keeps the Buildings tab (a building is added ahead of its units or by the first unit that names it, deleted only when empty, never renamed) and imports sheets of units or residents (checked whole, applied once within a day; a residents sheet is deleted once applied, found invalid or expired, and no one imported is emailed). A unit's page edits its building, floor, type and area (never its code) and shows its occupancy history (`residents.read`) and workers (`workers.review`). The unit picker lists the first 50 and finds any other by part of its code. The top bar's search (`/`) finds units, buildings, residents, staff, tickets (by `MT-` number) and assets, each kind only with the permission of its own list.
- Who is inside now (ADR 0056's update): the Gate page's "Inside now" tab (`/gate?tab=inside`, `gate.read`) lists every entry with no exit yet, across all gates, newest first, with the gate, the unit, since when, how many are inside and the guard's photo of the visitor when there is one (a presigned link, read again every 30 seconds, never stored). It reads `GET /gate/inside` with no shift; no name is shown. The overview's gate card keeps today's entries and shows "Inside now: N" on its link, N being the dashboard's `insideNow` (people, as the list counts them), read with the other cards in one call.
- A unit's closed mode needs `household.manage`, which only residents have, so the unit page leaves it out; its workers come from `GET /worker-engagements?unitId=` (ADR 0072).
- The client's IP reaches the API as the BFF's IP (no `X-Forwarded-For` is forwarded). Set it up at the reverse proxy if security events need the real client IP.
- A file is uploaded by the browser straight to object storage with a presigned URL (`components/file-upload.tsx`), so the bucket must allow the dashboard's origin (CORS: `PUT`, headers `Content-Type` and `If-None-Match`) and its URL must be reachable from the browser. Photos shown on a page come from presigned URLs the same way.
- A wage shows in the compound's currency, which the wage views name (`currency`, ISO 4217; the money formatter of the finance pages, `1,250.00 EGP` · `1,250.00 ج.م`), in the workers table, the engagement's wage line and its payments. Wage payments and closing a wage obligation are for manager accounts only (the API refuses a staff role, whatever it holds), so a staff reviewer sees the monthly wage and the open obligation without them.
- Requests to the management (ADR 0039): the inbox, a request's page, the appointments agenda and "Requests setup" need `requests.handle` or `requests.manage`; an account holding only one of them may sign in. Opening a request for a resident also needs `residents.read` and `units.read` (the resident is found through their unit, picked by part of its code). A request has no subject, so the inbox shows the start of its first message. Appointment slots are shown in the browser's time zone, the office hours are set in the compound's.
- Community life (ADR 0040): Announcements (with works and closures), Events and Polls need `community.publish`; Suggestions needs `community.suggestions`; "Community setup" shows the tab of whichever the account holds. An account holding only one of the two may sign in. Dates are typed and shown in the browser's time zone; "today" in the residents' daily brief is the compound's. A composer's audience count is of that moment: an audience is read again each time a resident opens the content. Read counts and poll results are counts only: there is no list of readers or of who chose what to show, by design; an open poll's counts stay hidden until five units have voted. Attachments are added one file at a time (up to five) and a removed one is dropped from the next version only. The dashboard has no rich text: titles and texts are plain, in English, Arabic or both.
- Neighbours (ADR 0042): Complaints, "Lost & found" (with the lending board) and "Conversation reports" need `neighbours.handle`, and an account holding only that may sign in; "Neighbours setup" needs `neighbours.manage`. A complaint has three threads that never mix — with the complainant, with the unit complained about (it opens with the one notice, whose text is the only thing the unit ever reads) and internal notes — each with its own compose box. The inbox's unit filter needs `units.read` and finds a unit by part of its code; its category filter lists active categories only. Only a found item is claimed and handed over; handing one to a resident who came without a claim finds them by part of the name, or the exact phone or email (`residents.read`), or takes a pasted account id. The lending board is read-only apart from removing a post, and no conversation between residents is reachable except as a reported case, which is readable only while the case is open. The welcome is written in English, Arabic or both, each language filled in completely or left empty.
- Facilities and the club (ADR 0044): "Facilities" needs `facilities.manage` (or `bookings.handle` to read it and its closures); "Bookings", "Approvals" and "Suspensions" need `bookings.handle`; "Memberships" needs `club.billing` and "Plans" `facilities.manage` or `club.billing`. An account holding only one of them may sign in; the accountant role holds `club.billing` alone. The day view shows one facility's local day in the browser's time zone (the compound's, in practice) and lists bookings that fit none of today's slots apart. Approving refuses past the slot's capacity as it is now. A closure's times are picked in the browser's local time. Memberships are listed whole (one per unit), not paged; a unit is found by its exact code. Staff cannot book on a resident's behalf, and there is no online payment.
- Vehicles and parking (ADR 0045): "Vehicles", "Visitor parking" and "Parking setup" need `vehicles.manage`; "Fines" needs `fines.issue` (issue, decide appeals, cancel) or `fines.billing` (read and record payments: the accountant); "Parking reports" needs `parking_reports.handle`, and turning one into a fine `fines.issue` too. An account holding only one of them may sign in, except `parking_reports.handle`: every guard holds it since ADR 0050 and closes reports from the app. A plate is searched by its key, so spaces and Arabic or Western digits do not matter. The visitor parking day is the browser's local day and its peak use counts confirmed bookings only. A fine is paid in full at the office; there is no online payment, and no replacement of a lost sticker (a plate edit voids it and the staff issue a new number).
- Emergencies and gate services (ADR 0047): "Emergencies" (live, every ten seconds) needs `emergencies.manage` or `emergencies.respond`; "Gate services" needs `gate_services.handle`; the Places tab of "Gate" and the office and duty phones of "Settings" need `gate.manage` and `settings.manage`. An account holding only one of them may sign in. Someone answering an emergency from here is not at a gate: the household sees the duty phone. There is no push to the browser: the sidebar counts and the pages refresh on a timer.
- Guard shifts and tasks (ADR 0050): "Roster" (single slots, weekly rosters, attendance), "Shift swaps" and "Handovers" (with the checklist) need `guard_roster.manage`; "Guard tasks" `guard_tasks.manage`; "Instructions" `guard_instructions.manage`; "Daily report" `guard_reports.read` (CSV through the BFF's download path); "Found at the gate" `found_items.manage`. An account holding only one of them may sign in: the security supervisor role holds the first four. Times are typed and shown in the browser's time zone (the compound's, in practice); a period is 31 days at most. A swap is decided only after the colleague accepted it, never by one of its two guards. Guards work from the app: nothing here starts a shift, takes a task or acknowledges. A found item is posted to the residents' board from "Lost & found" by hand.
- Patrols (ADR 0052): "Checkpoints" and "Patrol routes" need `patrols.manage`; "Patrol runs" and "Patrol report" need `patrols.manage` or `guard_reports.read`, and a run's track (where the guard walked) `patrols.manage` alone. A checkpoint's QR is shown once, when it is made or reissued, drawn in the browser from the payload and never sent anywhere: print it then (the same text goes on its NFC tag); a reissue makes the printed one stop scanning. A route's change is a new version: its runs nobody started are made again. The daily report gains each post's patrols. Guards walk the routes from the app: nothing here starts a run or scans.
- Children (ADR 0054): "Child alerts" needs `guard_roster.manage` and lists the unauthorized child pickups of the last 30 days (when, where, which guard, which unit, how the person was known), never the child; an alert's notice opens it. A plain exit is the household's record and never shows here. An event may be for children of an age range (set when it is written, fixed after); its page counts the children registered, and the attendees show how many per unit, never who. A bookable facility may take a child as a booking's occasion ("Children's occasions" in its rules); a booking shows only that there is one.
- Partners (ADR 0060): "Partners", "Partner requests", "Partner complaints" and "Partner settings" need `partners.manage`, and an account holding only that may sign in. A partner's services, hours and prices are each saved whole. Its desk link is shown once, when it is made or rotated: copy it then and give it to the partner; it expires after the compound's days (shown on the partner) and a rotation stops the old one at once. The requests page relays a partner's answer for a partner without a desk (accept, propose another time, decline, done, cancel), and shows what the partner would see: nothing of a request whose resident withdrew the consent. A complaint's conversation is the management request's, in "Requests"; here it is decided once. Suspending cancels the partner's live requests and tells the residents concerned; reinstating tells nobody. Hours are minutes in the compound's time zone; prices are announced in EGP and never charged.
- Assets and the maintenance store (ADR 0064, 0065): "Assets" and "Common areas" need `assets.read`; "Contracts" and "Economics" `assets.manage`; "Inspections" `inspections.manage`; "Stock" `stock.manage`. Of these, `assets.manage`, `inspections.manage` and `stock.manage` admit an account on their own; `assets.read` alone does not (every technician holds it and works from the app). Technicians scan tags, record readings and perform inspections from the app.
- Vendors and purchase requests (ADR 0077): "Vendors" needs `vendors.manage` (the register, its papers and suspensions); "Purchase requests" `purchases.approve` or `purchases.request` (a requester sees their own). `vendors.manage` and `purchases.approve` admit an account on their own; `purchases.request` alone does not (technicians ask from the app). A contract names a vendor of the register.
- Compliance and safety (ADR 0087): "Compliance" and "Compliance calendar" need `compliance.manage` (the manager's by default), which admits an account on its own: the items, their due days and evidence, the status report and its CSV; the vendors' papers show in the calendar. "Safety KPIs" needs `incidents.manage` or `guard_reports.read`. An incident's corrective actions are added in its dialog, and it closes only once none is open; "My corrective actions" lists the caller's own, with no permission. "Lockdown" gains "Lock down" for `lockdown.start` (the manager only), with the same typed confirmation as the guard's. A readiness item may be a drill, recorded with its outcome and headcount.
- Payables and commitments (ADR 0089): "Payables" needs `finance.payables` or `finance.payables_approve` (vendors' invoices, next month's payments, a contract's advances, retentions and guarantees); "Budget planning" `finance.budget` (transfers, a `budget_transfer` raised from its row, the year by period, commitments). - Energy and utilities (ADR 0066): "Meters", "Energy" and "Outages" need `energy.read`, and changing anything on them `energy.manage`; either admits an account. A unit's consumption shows when it stands empty, so `energy.read` is the supervisor's and the manager's by default. A technician records a meter's reading from the app with `meters.record`, which admits nobody here.
- Readiness and field safety (ADR 0067): "Readiness" needs `readiness.manage` and "Work permits" `safety.manage`; either admits an account. An item's owner marks their own item done with no permission; a technician acknowledges the safety instructions from the app before starting.
- Finance (ADR 0046, 0048, 0055, 0069): "Invoices", "Instalment plans", "Plan requests", "Disputes" and "Late notices" need `finance.invoice`; "Payments" and "Collector visits" `finance.payments`; "Billing plans" `finance.billing` or `finance.invoice`; "Refunds" `finance.refund` (manager only); "Ledger" and "Reports" `finance.reports`; "Budgets" and "Expenses" `finance.budget`; "Where the fees went" `finance.reports` or `finance.budget`; "Online payments" `finance.gateway`. All but `finance.refund` and `finance.gateway` (manager permissions) admit a staff account on their own: the accountant holds most of them. The field collector's `finance.collect` admits nobody here: the collector works their visits from the app, and the accountant assigns them under "Collector visits".
- Treasury and custody (ADR 0085): "Custody" needs `finance.payments` (the hand-ins) or `finance.custody` (settling a variance, investigations: the manager's); "Cheques" `finance.payments`; "Bank and cash" and "Bank statements" `finance.treasury` (the manager and the accountant). The collector reads their own custody from the app (`GET /collector/custody`).
- Guard vendors (ADR 0068): "Control room" needs `control_room.watch` (by default the security supervisor's): the guards' alerts and events, each taken once by whoever watches, and the posts at a glance. "Alarm wearables" needs `gate_devices.manage`: register a guard-down wearable, see its pairing, retire it with a reason. "Gate settings" (`gate.manage`) gains the face-check switch, to turn on only after a notice is posted at the gate, and the call times. Nothing here makes a call, scans an ID or checks a face: guards do that from the app.
- Community (ADR 0071): "Market" needs `market.handle` (by default the manager's): the listings waiting for review or reported, the reports, the shops and the market's settings; a resident's words show here and are never copied anywhere else, and a decision takes a code from its list. "Offers" shows group offers (`market.handle`) and partner offers (`partners.manage`): no money passes through Jiwar. "Daily life" needs `content.manage`: the compound's place and method for prayer times, the bus routes and their weekly departures, and the gallery's albums (staff photos; a privacy report hides one at once, here shown again or kept hidden with a code). A gate's directions are set on the gate (`gate.manage`); "Gate settings" gains how many entries in fifteen minutes make a gate read normal and busy.
- The manager's inbox, authority and deputy (ADR 0073): "Inbox" needs `inbox.read` (the manager's, the supervisors' and the accountant's by default) and lists, oldest first, what waits for a decision of a type the reader decides (each type its own permission), how long it waited, when it is due, and whether the board decides it (above a threshold); each row opens its own page, and the ones whose approval takes no input are approved together. "Inbox due times" (`settings.manage`) sets each type's hours. "Board settings" gains whether the waiver's and the payment plan's thresholds bind. "Deputy" (`deputies.manage`) names who decides in your place for up to 30 days, with permissions of your own role; either of you ends it.

An asset's timeline and "Planned work calendar" need `assets.read`; the warranty fields, its claims and "Warranty claims" `assets.manage`.
- The operations dashboard (ADR 0079): "Overview" needs `dashboard.read` (the manager's, the supervisors' and the accountant's by default) and reads its cards in one call: what waits for you, tickets and the SLA, emergencies, collections and what is owed, incidents, the gate's day, outages and units, each card only to a role that reads its part (liquidity in days of cover to a `finance.cashflow` holder, a dash when it cannot be computed). "Daily briefs" lists the morning briefs and end-of-day reviews, each shown by the reader's own parts; their times are the managers' (`settings.manage`). - Fit-out (ADR 0074): a works permit's page (`permits.manage`) shows its fit-out — the finishing-works deposit recorded for it (recording one needs `deposits.manage`), what blocks its completion certificate, the drawings, the debris removals (schedule, done, call off), the common areas before and after the works, and the damage claims (raise, decide the appeal, withdraw, and settle with a step-up). - Spaces (ADR 0084): "Holidays", "Site map" and "Floor plans" need `spaces.manage`; the permit settings' days off are read-only there and open the holiday calendar. The planned work calendar flags a date on a holiday.
- Announcements and the office queue (ADR 0080): an announcement's delivery card and "Remind who has not opened it" need `community.publish`; a request's "Change topic" `requests.handle`, "Turn into a ticket" also `tickets.dispatch`; "Message templates" `community.publish` (announcements) or `requests.manage` (replies); "Official letters" `letters.issue`; a unit's "Correspondence" `correspondence.read`. "Start a conversation" on the requests to the management (`POST /management/outreach`; `requests.handle`, `residents.read` and `units.read`) finds the resident through their unit, takes a topic, the message and up to five files, and opens the request it started: it starts answered and waits for the resident.
- Maintenance analytics and cases (ADR 0081): "Repeat faults", "Complaints map" and "Community cases" need `tickets.dispatch`: a category's repairs per asset, unit, building or common area over a period from the compound's threshold on; each building's and common area's tickets (counts only; a building opens the ticket list filtered by it); the cases a building's reports opened, with their one work order, resolved (the reporters told) or dismissed. The four numbers sit in Maintenance setup → SLA → Analytics (`maintenance.manage`).
- Experience and recovery (ADR 0082): "Resident experience" (`/experience`: the cases and signals, "Open a case", a case's owner, compensations and close), its "Setup" (the rules' thresholds, the compensation recommended per failure, the service promises) and "Reports" need `experience.manage`; so does "Compensations". A credit picks the unit's invoice from its invoices (newest first, "load more") and, above the board's binding limit, the board's authorization from those approved for a compensation and still unused (both are finance's, `finance.invoice`, the manager's; an account without it types the ids).
- Transfers, dues and closed units (ADR 0083): a unit's "Transfer ownership" now requests the transfer; "Ownership transfers" (`residents.manage`) approves it once, past the dues check: a unit that owes the compound is approved only as an exception, with a reason and a fresh code to your email. "Moves" shows what each unit owes. A unit's papers end a proxy with a reason (the proxy and the owner are told). "Closed units" and "Emergency entries" need `guard_tasks.manage`: a closed unit's round falls due every few days ("Gate settings" sets how many) and is scheduled as a guard's inspection; an emergency entry tells the unit's people as it is saved, and its report is due within a day. "Market" settings gain the commercial block, the categories taken and the listings per unit; "Offers" records a confirmed group offer's contract, and above the group price the households re-confirm or drop out.
- The field team (ADR 0078): "Field team" needs `field_team.manage` (by default the manager and the maintenance supervisor): the technicians' calls for help, taken with a colleague sent or none and resolved; their roster (single slots here, in a zone or for the whole compound; going on duty fills a slot, going off closes it) and attendance; and the instructions every technician acknowledges. A call's note is the technician's own words and shows only here.
- The field team, part b (ADR 0090): "Field team" gains Reinforcement (service pressure's suggestion, a call to the technicians off duty, its answers and its call-off), Certificates (the staff's, with their expiry and their paper, filed, read, replaced or removed; warned of, never blocking) and Location (a technician's last known location, one at a time, read only with their consent and audited). "Access checks" needs `accounts.manage`: the accounts of the compound's side that look dangling, kept with a code or deactivated, the open access review with each line kept or revoked (revoking deactivates the account), and the two settings.
- The reports platform (ADR 0086): "Reports" lists the reports the reader's own permissions open (maintenance spend `assets.manage`, stock `stock.manage`, service by building `tickets.dispatch`, energy cost per m² `energy.read`, collections `finance.reports`), over a period, grouped, compared with the period before or a year earlier, and as PDF, Excel or CSV. "Scheduled reports" (`reports.schedule`, the manager's) sends one daily, weekly or monthly; "Sent reports" holds each run's file for 90 days, opened by whoever may read the report. "Capital plans" (`assets.manage`) draws a year's plan and submits it to the board once (`governance.approvals`); approved, it is locked. "Compound export" (`compound.export`) asks for the compound's operational data after a fresh code, once a day; no one's personal data is in it.
- Cash flow (ADR 0091): "Cash flow" (`/finance/cash-flow`) needs `finance.cashflow` (the manager's and the accountant's by default): from today, by week (Saturday to Friday) or month, the accounts' balances, what payables already schedules out and the residents' dues at the 90-day collection rate in, each period's closing against the minimum, and its CSV. "Minimum cash" needs `finance.treasury`. Unscheduled spending (salaries, utilities) is not forecast; with no dues in the last 90 days nothing is expected from the residents. The realised cash flow is the `cash_flow` report.
- The general ledger (ADR 0092): "Chart of accounts", "Financial statements", "Journal entries" and "Closing months" need `finance.ledger` (the manager's and the accountant's by default); writing needs `finance.ledger_write`, reopening a month `finance.ledger_reopen` (the manager's). Every money event posts its own entry; the chart shows each account's balance on a day and the reconciliation with the registers (a difference other than zero is a fault). A manual entry is approved by someone other than its maker, on accounts no register keeps: bank and cash, receivables, unit credit, deposits, payables, retentions and advances are corrected in their registers. Not built here: adding a top-level account (sub-accounts only), changing a code. The year-end closing entry is ADR 0093's, below. The journal of a period is paged, 50 entries at a time. ADR 0048's "Ledger" page is the units' computed journal and stays.
- Taxes and the year-end close (ADR 0093): "Tax settings" (`/finance/tax`), "VAT declaration" and "Withholding tax" need `finance.ledger` (the manager's and the accountant's by default); changing the settings, declaring a month, paying a tax, a vendor's withholding category and closing a fiscal year need `finance.ledger_write`; reopening a closed year `finance.ledger_reopen` (the manager's). VAT is off until the compound registers (14 % when on); no invoice kind is taxable and no purchase category recoverable until the compound marks them; withholding is off (supplies 1 %, services 3 %, professional fees 5 %, from 300 EGP): the defaults are common Egyptian practice and the compound's to change. A month is declared once the ledger has closed it, in order, then its figures are locked; the VAT due and each quarter's tax withheld are paid from a bank or cash account (choosing one needs `finance.treasury`). Each withholding certificate is a PDF for the vendor. "Closing months" also closes and reopens fiscal years (the first month is set on "Budgets"). Not built: filing with the tax authority, a taxable flag per fee item, a refund of a VAT credit (it carries forward), and other taxes.
- Purchase orders (ADR 0094): "Purchase orders" (`/purchase-orders`) needs `purchase_orders.raise`, `purchase_orders.receive` or `purchases.approve`; raising, amending, sending and cancelling the rest need `purchase_orders.raise` (the manager's, the accountant's and the maintenance supervisor's), approving `purchases.approve` (never the raiser's own order, even under the board's approval), receiving `purchase_orders.receive`. The vendor invoice page shows the three-way match and lets a mismatch through with `finance.match_override` (the manager's, never an invoice the caller recorded); the tolerances at `/purchase-orders/settings` need `finance.payables_approve` to change. The budget line picker reads with `finance.budget` or `purchase_orders.raise`, and the stock item picker with `stock.manage` or `purchase_orders.raise`, so every role that raises orders fills the whole form. Known limits: the receiving page shows what is still to come without the quantity tolerance (the API's refusal gives the maximum); the order page shows the budget line by id only; a vendor's contractors have no page, only the API; sending an order records it and tells the contractors, no email is sent.
- Topic names are entered in English and Arabic (the residents' app shows the Arabic one); the Arabic field is the only right-to-left input.
- Not translated: the text a manager types (announcements, notes, topic names in the language they are written), the fields the API holds in English only (a board publication's `titleEn` / `bodyEn`), the permission codes shown beside their plain words on the roles page, and the CSV files' column names and file names.

- Tenders (ADR 0088): a tender's page adds and removes its documents (`tender_document`), invites a registered vendor or makes a bid link (shown once), renews a link (the old one stops) or revokes an invitation, moves the deadline later, and awards an opened bid (the board's approved major contract picked above the manager's limit, for `governance.approvals` holders). A vendor's page lists its contractors, invites one (`vendors.manage`) and switches one off or on (`accounts.manage`); a queued ticket's page offers it to a vendor with a note, lists its offers and takes an open one back (`tickets.dispatch`; naming the vendor needs a permission that reads the register). The bid link's page is the public app's `/b#<token>` (`apps/public`), where the company attaches its bid's documents; the tender's page shows each opened bid's documents (none before the opening: they are sealed with the bid).

## Arabic and English

The owner's decision of 2026-11-10: the dashboards and the public pages speak Arabic and English, **Arabic by default**, right to left. A language switch sits in the top bar (and on the sign-in pages); the choice is kept in the `jiwar_locale` cookie (one year, `SameSite=Lax`, holds the choice and nothing else).

- **The layer** is `packages/i18n`, with no dependency: the locale (`ar`, `en`; anything else reads as `ar`), the cookie, a small ICU subset for messages (`{name}`, Arabic plurals with every form, `select`; values are isolated in their own direction), `I18nProvider`, `useT(en, ar)`, `useFormat()`, and the test helpers.
- **The locale is not in the URLs.** The root layouts read the cookie on the server and render `<html lang dir>` with it, so the first paint is already in the right direction. The public pages are not indexed (`noindex`) and carry a token in the fragment, so locale-prefixed URLs would buy nothing and would break the links the API emails.
- **Catalogs**, one file per page or feature, English as the source and Arabic typed against it (a missing or extra key does not compile):
  - `apps/<app>/messages/{en,ar}/*.ts` for each app (the public app keeps `messages/{ar,en}.ts`);
  - `packages/ui/src/messages` for the shared words and the labels of the API's codes (statuses, kinds, reasons; `useLabel()`);
  - `packages/api/src/messages` for the API's error codes and field errors (`errorText`, `fieldError`, `ErrorText`), with a fallback for an unknown code.
- **Formatting** is in one place, `useFormat()` (`packages/i18n/src/format.ts`): dates and times in the browser's zone (the compound's, as before; the public pages pass the compound's zone), plain `YYYY-MM-DD` days never shifted, relative times, numbers, `EGP` / `ج.م` amounts, percentages and lists. Arabic uses `ar-EG` with **Western digits** (`nu-latn`): codes, references, phone numbers, plates and amounts are typed and printed in Western digits, so a row never mixes two systems, money columns line up and compare at a glance, and a copy into a spreadsheet stays a number.
- **Right to left** is in the shared components: logical properties (start and end) in `packages/ui/src/styles.css`, `.icon-dir` mirrors an icon that points a way, `.ltr` keeps a code or a number left to right inside Arabic text, email, phone, link, number and password inputs read left to right. The dashboards' Arabic face is IBM Plex Sans Arabic.
- **Tests** (`pnpm dashboards:test`): every catalog has the same files, keys and `{values}` in both languages, no empty text, the Arabic is Arabic; and a scan (`@jiwar/i18n/testing`, `findHardCodedText`) fails on any text left in a component outside the catalogs, in the three apps and in the shared packages. To see the text left in a file: `node --experimental-strip-types packages/i18n/src/scan-cli.ts <files or folders>`. `pnpm dashboards:test` also runs `@jiwar/admin`, `@jiwar/i18n`, `@jiwar/ui` and `@jiwar/api`, each with its own light tests (no network, no API server).
- **Adding a text:** add the key to `messages/en/<page>.ts`, then to `messages/ar/<page>.ts`, and use `const t = useT(en, ar)`. Never build a sentence from pieces; give the whole sentence with `{values}` and let Arabic reorder it. Counts use `plural`.
