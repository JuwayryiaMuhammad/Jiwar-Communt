# Dashboards

Two Next.js 16 dashboards for this backend, in the same pnpm workspace (`pnpm-workspace.yaml` at the repo root):

| App | Port | Who | Sign-in |
|---|---|---|---|
| `apps/admin` | 3001 | Platform super admin | Email + password (`/platform/auth/*`), forced password change on first sign-in |
| `apps/manager` | 3002 | Compound manager, maintenance supervisor | Email or phone → 6-digit code by email → pick the account. Admitted: managers, and any role holding one of the entry permissions (`ENTRY_PERMISSIONS` in `apps/manager/lib/access.ts`, read from `GET /me` at sign-in); anyone else is signed out at once and shown "No access" |

Both follow the design system in `docs/decisions/DESIGN.md`. The tokens live in `packages/ui/src/styles.css`.

```
apps/admin        super admin: compounds, managers, security events, platform audit, account
apps/manager      manager: overview, requests, units, residents, workers, maintenance, gate, parcels, partners, staff, accounts, roles, settings, maintenance setup, deletion requests, audit, notifications, own account
apps/public       the public web pages the API's links open (port 3003); not a dashboard, see apps/public/README.md
apps/Dockerfile   one image per app (--build-arg APP=admin|manager|public), Next.js standalone output
packages/ui       design tokens + components (shell, cards, tables, dialogs, forms, toasts)
packages/api      types generated from docs/api/openapi.v0.json, typed client, error texts, React data hooks
packages/bff      server-only: cookie session, /bff proxy, single-flight token refresh, CSRF guard
```

## Run

With Docker, `docker compose up -d --build` at the repo root starts the API and both dashboards (root README).

On the host, against an API on the host or in Docker:

```bash
pnpm install                                         # at the repo root, once
cp apps/admin/.env.example apps/admin/.env.local     # JIWAR_API_URL, e.g. http://localhost:3100
cp apps/manager/.env.example apps/manager/.env.local
pnpm dev:admin       # http://localhost:3001
pnpm dev:manager     # http://localhost:3002
```

`JIWAR_API_URL` is the API origin without `/api/v1`, read on the server only.

After an API change (`pnpm openapi:export`), regenerate the client types; CI fails while they are stale:

```bash
pnpm api:generate
pnpm dashboards:typecheck
```

## How the dashboards talk to the API (BFF)

The browser never holds a token and never calls the API. Each app has a backend-for-frontend under `/bff`:

- `/bff/auth/*`: sign-in, sign-out and session routes. Tokens go into httpOnly cookies: the access token and refresh token are scoped to `/bff`, and a secret-free marker cookie on `/` lets `proxy.ts` send signed-out visitors to `/login`.
- `/bff/api/v1/...`: forwards an allow-listed call with `Authorization: Bearer`. The admin app forwards `/api/v1/platform/*` only (not `platform/auth`). The manager app forwards everything except `platform`, `auth`, `public` and the public invite and registration flows. A path with `.` or `..` segments gets 404. Error bodies are passed through without the API's developer `message` and `path`.
- **Refresh.** The API rotates refresh tokens and revokes the session when a rotated token comes back (reuse detection, ADR 0004). The BFF therefore refreshes each token once (single flight). For 30 s afterwards it hands the same result to late requests that still carry the old cookie. A 401 is retried once after a refresh; the auth guard rejects before any handler runs, so the retry cannot repeat a side effect. The refresh state is per process, so run one BFF instance per app or use sticky sessions.
- **CSRF.** Every `/bff` call must carry `x-jiwar-bff: 1`, a custom header that forces a CORS preflight the BFF never answers. Non-GET calls must come from the same `Origin`. Cookies are `SameSite=Lax`, or `Strict` for the login ticket.

Because of the BFF, the API needs no `CORS_ORIGINS` for the dashboards.

## Permissions

`GET /me` returns the role's permissions. The shell shows a section only to a role that may read it, and asks for a queue's count only then (`lib/permissions.tsx`: `usePermissions`, `Can`). This is for showing and hiding; the API decides every call, and a 403 renders as "No access" where it lands.

## Known limits (API v0)

- A ticket opened for a resident in a common area takes its reporter from the first 100 residents (for a unit, the API lists who may report there).

- The overview's numbers come from the dashboard's summary (ADR 0079), counted in the database; other pages' counts still come from one page of up to 100 rows and show `100+` beyond that.
- The unit register (ADR 0072): Units searches by part of the code, and the manager (`units.manage`) filters by building and status, downloads the CSV, keeps the Buildings tab (a building is added ahead of its units or by the first unit that names it, deleted only when empty, never renamed) and imports sheets of units or residents (checked whole, applied once within a day; a residents sheet is deleted once applied, found invalid or expired, and no one imported is emailed). A unit's page edits its building, floor, type and area (never its code) and shows its occupancy history (`residents.read`) and workers (`workers.review`). The unit picker still lists the first 100 units by code. The top bar's search (`/`) finds units, buildings, residents, staff, tickets (by `MT-` number) and assets, each kind only with the permission of its own list.
- Managers cannot read `GET /gate/inside` (it needs `gate.operate`, which only guards have), so the overview shows today's entries instead of who is inside.
- A unit's closed mode needs `household.manage`, which only residents have, so the unit page leaves it out; its workers come from `GET /worker-engagements?unitId=` (ADR 0072).
- The client's IP reaches the API as the BFF's IP (no `X-Forwarded-For` is forwarded). Set it up at the reverse proxy if security events need the real client IP.
- A file is uploaded by the browser straight to object storage with a presigned URL (`components/file-upload.tsx`), so the bucket must allow the dashboard's origin (CORS: `PUT`, headers `Content-Type` and `If-None-Match`) and its URL must be reachable from the browser. Photos shown on a page come from presigned URLs the same way.
- A wage has no currency: the API does not name the compound's, so amounts show as plain numbers. Wage payments and closing a wage obligation are for manager accounts only (the API refuses a staff role, whatever it holds), so a staff reviewer sees the monthly wage and the open obligation without them.
- Requests to the management (ADR 0039): the inbox, a request's page, the appointments agenda and "Requests setup" need `requests.handle` or `requests.manage`; an account holding only one of them may sign in. Opening a request for a resident also needs `residents.read` and `units.read` (the resident is found through their unit, from the first 100 units). A request has no subject, so the inbox shows the start of its first message. Appointment slots are shown in the browser's time zone, the office hours are set in the compound's.
- Community life (ADR 0040): Announcements (with works and closures), Events and Polls need `community.publish`; Suggestions needs `community.suggestions`; "Community setup" shows the tab of whichever the account holds. An account holding only one of the two may sign in. Dates are typed and shown in the browser's time zone; "today" in the residents' daily brief is the compound's. A composer's audience count is of that moment: an audience is read again each time a resident opens the content. Read counts and poll results are counts only: there is no list of readers or of who chose what to show, by design; an open poll's counts stay hidden until five units have voted. Attachments are added one file at a time (up to five) and a removed one is dropped from the next version only. The dashboard has no rich text: titles and texts are plain, in English, Arabic or both.
- Neighbours (ADR 0042): Complaints, "Lost & found" (with the lending board) and "Conversation reports" need `neighbours.handle`, and an account holding only that may sign in; "Neighbours setup" needs `neighbours.manage`. A complaint has three threads that never mix — with the complainant, with the unit complained about (it opens with the one notice, whose text is the only thing the unit ever reads) and internal notes — each with its own compose box. The inbox's unit filter needs `units.read` and lists the first 100 units; its category filter lists active categories only. Only a found item is claimed and handed over; handing one to a resident who came without a claim picks them from the first 100 residents (`residents.read`) or takes a pasted account id. The lending board is read-only apart from removing a post, and no conversation between residents is reachable except as a reported case, which is readable only while the case is open. The welcome is written in English, Arabic or both, each language filled in completely or left empty.
- Facilities and the club (ADR 0044): "Facilities" needs `facilities.manage` (or `bookings.handle` to read it and its closures); "Bookings", "Approvals" and "Suspensions" need `bookings.handle`; "Memberships" needs `club.billing` and "Plans" `facilities.manage` or `club.billing`. An account holding only one of them may sign in; the accountant role holds `club.billing` alone. The day view shows one facility's local day in the browser's time zone (the compound's, in practice) and lists bookings that fit none of today's slots apart. Approving refuses past the slot's capacity as it is now. A closure's times are picked in the browser's local time. Memberships are listed whole (one per unit), not paged; a unit is found by its exact code. Staff cannot book on a resident's behalf, and there is no online payment.
- Vehicles and parking (ADR 0045): "Vehicles", "Visitor parking" and "Parking setup" need `vehicles.manage`; "Fines" needs `fines.issue` (issue, decide appeals, cancel) or `fines.billing` (read and record payments: the accountant); "Parking reports" needs `parking_reports.handle`, and turning one into a fine `fines.issue` too. An account holding only one of them may sign in, except `parking_reports.handle`: every guard holds it since ADR 0050 and closes reports from the app. A plate is searched by its key, so spaces and Arabic or Western digits do not matter. The visitor parking day is the browser's local day and its peak use counts confirmed bookings only. A fine is paid in full at the office; there is no online payment, and no replacement of a lost sticker (a plate edit voids it and the staff issue a new number).
- Emergencies and gate services (ADR 0047): "Emergencies" (live, every ten seconds) needs `emergencies.manage` or `emergencies.respond`; "Gate services" needs `gate_services.handle`; the Places tab of "Gate" and the office and duty phones of "Settings" need `gate.manage` and `settings.manage`. An account holding only one of them may sign in. Someone answering an emergency from here is not at a gate: the household sees the duty phone. There is no push to the browser: the sidebar counts and the pages refresh on a timer.
- Guard shifts and tasks (ADR 0050): "Roster" (single slots, weekly rosters, attendance), "Shift swaps" and "Handovers" (with the checklist) need `guard_roster.manage`; "Guard tasks" `guard_tasks.manage`; "Instructions" `guard_instructions.manage`; "Daily report" `guard_reports.read` (CSV through the BFF's download path); "Found at the gate" `found_items.manage`. An account holding only one of them may sign in: the security supervisor role holds the first four. Times are typed and shown in the browser's time zone (the compound's, in practice); a period is 31 days at most. A swap is decided only after the colleague accepted it, never by one of its two guards. Guards work from the app: nothing here starts a shift, takes a task or acknowledges. A found item is posted to the residents' board from "Lost & found" by hand.
- Patrols (ADR 0052): "Checkpoints" and "Patrol routes" need `patrols.manage`; "Patrol runs" and "Patrol report" need `patrols.manage` or `guard_reports.read`, and a run's track (where the guard walked) `patrols.manage` alone. A checkpoint's QR is shown once, when it is made or reissued, drawn in the browser from the payload and never sent anywhere: print it then (the same text goes on its NFC tag); a reissue makes the printed one stop scanning. A route's change is a new version: its runs nobody started are made again. The daily report gains each post's patrols. Guards walk the routes from the app: nothing here starts a run or scans.
- Children (ADR 0054): "Child alerts" needs `guard_roster.manage` and lists the unauthorized child pickups of the last 30 days (when, where, which guard, which unit, how the person was known), never the child; an alert's notice opens it. A plain exit is the household's record and never shows here. An event may be for children of an age range (set when it is written, fixed after); its page counts the children registered, and the attendees show how many per unit, never who. A bookable facility may take a child as a booking's occasion ("Children's occasions" in its rules); a booking shows only that there is one.
- Partners (ADR 0060): "Partners", "Partner requests", "Partner complaints" and "Partner settings" need `partners.manage`, and an account holding only that may sign in. A partner's services, hours and prices are each saved whole. Its desk link is shown once, when it is made or rotated: copy it then and give it to the partner; it expires after the compound's days (shown on the partner) and a rotation stops the old one at once. The requests page relays a partner's answer for a partner without a desk (accept, propose another time, decline, done, cancel), and shows what the partner would see: nothing of a request whose resident withdrew the consent. A complaint's conversation is the management request's, in "Requests"; here it is decided once. Suspending cancels the partner's live requests and tells the residents concerned; reinstating tells nobody. Hours are minutes in the compound's time zone; prices are announced in EGP and never charged.
- Assets and the maintenance store (ADR 0064, 0065): "Assets" and "Common areas" need `assets.read`; "Contracts" and "Economics" `assets.manage`; "Inspections" `inspections.manage`; "Stock" `stock.manage`. Of these, `assets.manage`, `inspections.manage` and `stock.manage` admit an account on their own; `assets.read` alone does not (every technician holds it and works from the app). Technicians scan tags, record readings and perform inspections from the app.
- Vendors and purchase requests (ADR 0077): "Vendors" needs `vendors.manage` (the register, its papers and suspensions); "Purchase requests" `purchases.approve` or `purchases.request` (a requester sees their own). `vendors.manage` and `purchases.approve` admit an account on their own; `purchases.request` alone does not (technicians ask from the app). A contract names a vendor of the register.
- Energy and utilities (ADR 0066): "Meters", "Energy" and "Outages" need `energy.read`, and changing anything on them `energy.manage`; either admits an account. A unit's consumption shows when it stands empty, so `energy.read` is the supervisor's and the manager's by default. A technician records a meter's reading from the app with `meters.record`, which admits nobody here.
- Readiness and field safety (ADR 0067): "Readiness" needs `readiness.manage` and "Work permits" `safety.manage`; either admits an account. An item's owner marks their own item done with no permission; a technician acknowledges the safety instructions from the app before starting.
- Finance (ADR 0046, 0048, 0055, 0069): "Invoices", "Instalment plans", "Plan requests", "Disputes" and "Late notices" need `finance.invoice`; "Payments" and "Collector visits" `finance.payments`; "Billing plans" `finance.billing` or `finance.invoice`; "Refunds" `finance.refund` (manager only); "Ledger" and "Reports" `finance.reports`; "Budgets" and "Expenses" `finance.budget`; "Where the fees went" `finance.reports` or `finance.budget`; "Online payments" `finance.gateway`. All but `finance.refund` and `finance.gateway` (manager permissions) admit a staff account on their own: the accountant holds most of them. The field collector's `finance.collect` admits nobody here: the collector works their visits from the app, and the accountant assigns them under "Collector visits".
- Guard vendors (ADR 0068): "Control room" needs `control_room.watch` (by default the security supervisor's): the guards' alerts and events, each taken once by whoever watches, and the posts at a glance. "Alarm wearables" needs `gate_devices.manage`: register a guard-down wearable, see its pairing, retire it with a reason. "Gate settings" (`gate.manage`) gains the face-check switch, to turn on only after a notice is posted at the gate, and the call times. Nothing here makes a call, scans an ID or checks a face: guards do that from the app.
- Community (ADR 0071): "Market" needs `market.handle` (by default the manager's): the listings waiting for review or reported, the reports, the shops and the market's settings; a resident's words show here and are never copied anywhere else, and a decision takes a code from its list. "Offers" shows group offers (`market.handle`) and partner offers (`partners.manage`): no money passes through Jiwar. "Daily life" needs `content.manage`: the compound's place and method for prayer times, the bus routes and their weekly departures, and the gallery's albums (staff photos; a privacy report hides one at once, here shown again or kept hidden with a code). A gate's directions are set on the gate (`gate.manage`); "Gate settings" gains how many entries in fifteen minutes make a gate read normal and busy.
- The manager's inbox, authority and deputy (ADR 0073): "Inbox" needs `inbox.read` (the manager's, the supervisors' and the accountant's by default) and lists, oldest first, what waits for a decision of a type the reader decides (each type its own permission), how long it waited, when it is due, and whether the board decides it (above a threshold); each row opens its own page, and the ones whose approval takes no input are approved together. "Inbox due times" (`settings.manage`) sets each type's hours. "Board settings" gains whether the waiver's and the payment plan's thresholds bind. "Deputy" (`deputies.manage`) names who decides in your place for up to 30 days, with permissions of your own role; either of you ends it.
- Dispatch depth (ADR 0076): "New work order" on Maintenance, the list's building and search filters and "Export 30 days", and a ticket's "Close for the residents", "Reopen" and "Resume" need `tickets.dispatch`; so does "SLA report". The escalation levels sit in Maintenance setup → SLA (`maintenance.manage`). An asset's timeline and "Planned work calendar" need `assets.read`; the warranty fields, its claims and "Warranty claims" `assets.manage`.
- The operations dashboard (ADR 0079): "Overview" needs `dashboard.read` (the manager's, the supervisors' and the accountant's by default) and reads its cards in one call: what waits for you, tickets and the SLA, emergencies, collections and what is owed, incidents, the gate's day, outages and units, each card only to a role that reads its part (liquidity shows a dash until cash flow exists). "Needs you now" lists the critical alerts, then the inbox's overdue items; "Buildings" bands each building of the register. "Daily briefs" lists the morning briefs and end-of-day reviews, each shown by the reader's own parts; their times are the managers' (`settings.manage`). "Gate traffic" (`gate.read`) and "Gate log search" (`gate_log.search`, a visitor's full name exactly, never a part; its CSV goes by the request's body) open the gate's reports. The service-pressure threshold sits in Maintenance setup → Dispatch (`maintenance.manage`).
- Fit-out (ADR 0074): a works permit's page (`permits.manage`) shows its fit-out — the finishing-works deposit recorded for it (recording one needs `deposits.manage`), what blocks its completion certificate, the drawings, the debris removals (schedule, done, call off), the common areas before and after the works, and the damage claims (raise, decide the appeal, withdraw, and settle with a step-up). "Permit settings" holds whether works wait for their deposit.
- Topic names are entered in English and Arabic (the residents' app shows the Arabic one); the Arabic field is the only right-to-left input.
- English only for now. Error texts are keyed by API error code in `packages/api/src/errors.ts`, ready for an Arabic dictionary.
