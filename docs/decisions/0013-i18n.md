# 0013 — Internationalization (Arabic + English)

**Status:** Accepted · Phase 1a

## Decision
The backend never returns user-facing display text. It returns stable codes and keys; the frontend translates.

- **Errors:** every error response has a machine `code`, optional `params`, and for validation or duplicate values `fields: [{ field, code, params? }]` (e.g. `FIELD_REQUIRED`, `INVALID_PHONE`, `DUPLICATE_VALUE`). `message` is English, for developers only. `AppException` is the only exception type in `src/` — a unit test fails on anything else.
- **Database errors** map to stable codes (`DUPLICATE_RESOURCE`, `RELATED_RESOURCE_MISSING`, `NOT_FOUND`); anything else is `INTERNAL_ERROR`. Database text (table, column, constraint names) is never returned. Unique-index → field names live in `src/common/db-constraints.ts`, kept complete by a DB test; primary-key collisions stay neutral (ADR 0006).
- **Successful responses** that exist only to inform carry a code too (e.g. `OTP_REQUESTED`).
- **System data by key:** default roles and permissions are identified by `key`; no Arabic or English display strings are stored for system data (`roles.name` is only for future custom roles).
- **Locale:** `preferred_locale` (`ar` | `en`, default `ar`) on `accounts` and `platform_admins`. Where the account is not proven yet (OTP request) the `Accept-Language` header decides, falling back to Arabic.
- **Emails** the server sends (OTP) have Arabic (RTL) and English templates.

## Out of scope
UI translation; bilingual names for compounds and units (decided with the design).
