# 0029 — Object storage: a private bucket, presigned uploads checked at finalize

**Status:** Accepted · Phase 4.2

## Context
Worker photos (ADR 0030 left them for later), identity scans and registration documents need files. Almost every file here is personal data, and every compound is a tenant. Production storage is Cloudflare R2; development, tests and CI use MinIO. Both speak the S3 API. An earlier branch (`storage-wip`, never merged) took the bytes through the server in multipart requests. That design is replaced here: R2 does not support presigned POST, and the bytes do not need to pass through the API.

## Decisions

### The store
- **One S3 client** (AWS SDK v3), configured only by `S3_*`: `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE`, `S3_URL_TTL_SECONDS` (default 300, at most 3600). R2 and MinIO differ only in these values (R2: `https://<account>.r2.cloudflarestorage.com`, region `auto`). Nothing in `src/` reads an `R2_*` variable; a unit test checks this.
- **R2 compatibility:** no object ACLs (R2 has none); `requestChecksumCalculation` and `responseChecksumValidation` are `WHEN_REQUIRED`, because newer SDKs add CRC headers that R2 rejects on some operations and that a browser's PUT cannot send. Connection and request timeouts are short (3 s, 10 s), so a stalled store fails a request instead of holding it.
- **The bucket is private.** No file has a public URL, and r2.dev access stays off. Reads are presigned GETs valid for `S3_URL_TTL_SECONDS`. They are returned only in no-store responses.
- **A store failure is `STORAGE_UNAVAILABLE` (503).** It is logged by error name only, and the store's message never reaches a response.
- The settings are required. `.env.example`, CI and the test environment set MinIO values, so a fresh clone boots. Boot never contacts the store.

### Uploads
1. `POST /files/uploads {purpose, contentType, size}` checks the purpose's types, limit and uploader permission. It returns a presigned **PUT** with `Content-Type`, `Content-Length` and `If-None-Match: *` signed in (no-store). The store refuses another type or size. It also refuses a second PUT to the same key, so the bytes checked at finalize can never be swapped afterwards. MinIO enforces all three, and the R2 smoke test checks R2.
2. The client PUTs the bytes straight to the store.
3. `POST /files/:id/finalize` makes three checks with a HEAD and a ranged GET of the first 16 bytes: the size, the stored type, and the magic bytes against the declared type. A file that passes is `ready`. One that fails is deleted at once (`FILE_CONTENT_MISMATCH`, 422). Calling finalize before the PUT is `FILE_UPLOAD_MISSING` (409), and the file keeps waiting. Calling it more than 15 minutes after the URL expired is `FILE_UPLOAD_EXPIRED` (409). The grace exists because a PUT is checked when it starts, so a slow upload can finish after its URL expires. Finalizing a ready file again is a no-op.
4. **Object keys are `t/<tenantId>/<fileId>`.** The id is generated by the server, and the key is derived from the row, never stored. Nothing a client sends is ever part of a key. The uploader's file name is not kept.

### Purposes
| Purpose | Types | Limit | Who uploads |
|---|---|---|---|
| `worker_photo` | JPEG, PNG, WebP | 5 MB | `workers.manage` (whoever registers a worker) or `workers.review` (the manager sets or replaces it) |
| `document` | JPEG, PNG, WebP, PDF | 10 MB | `accounts.manage` (management) |

The database repeats types and limits as CHECKs, and a unit test keeps the two in step.

### The files table
- `files` is a tenant table with RLS and FORCE, like every tenant table. It holds the owner, the purpose, the declared type and size, the `pending`/`ready` status, the upload's expiry, `finalized_at` and `deleted_at`.
- **Everything is the owner's own:** `GET /files/:id` (with a read URL once ready, no-store), finalize and `DELETE /files/:id`. Another account's file, another compound's file and a deleted file are all `FILE_NOT_FOUND`. Features return URLs for their files in their own views, under their own rules.
- **At most 10 live unfinalized uploads per account** (`FILE_PENDING_LIMIT`, 429), counted under the account's row lock so parallel requests cannot pass the limit together. An expired upload stops counting.
- **Audit:** `file.created` records `{purpose, contentType, size}`. `file.deleted` records `{purpose, reasonCode}`, where the reason is `owner`, `content_mismatch`, `upload_expired` or `erasure`. No file name and no URL is ever recorded.

### Deletion, the sweep, erasure
- **Deleting a file takes three steps.** The row is marked `deleted_at` in the action's transaction (audited). After commit the object is deleted, then the row. If the object delete fails, the row stays and the sweep tries again. **An object never outlives the row that names it.**
- **The `files.cleanup` sweep** first marks uploads never finalized an hour after their URL expired (`upload_expired`, actor `system`). Then it deletes the objects of deleted rows, and each row only after its object delete succeeded. Store calls run between two tenant transactions, never inside one.
- **Races:** finalize, delete and the sweep each lock the row (`FOR UPDATE`). The sweep uses `SKIP LOCKED` and comes long after finalize's grace, so it never takes a file a finalize is working on. A finalize that loses to a delete or the sweep gets `FILE_NOT_FOUND`. Store calls in finalize happen before its transaction, so no database connection waits on the network.
- **Erasure (ADR 0023)** marks the account's own files deleted in the erasure's transaction and deletes their objects after it commits. A rolled-back erasure deletes nothing.

### Local, CI, smoke test
- MinIO runs in docker-compose (API 9005, console 9006). The official images are no longer published, so it is the `pgsty/minio` community build, pinned like on staging. `pnpm storage:init` creates the dev bucket and is refused in production.
- e2e tests always use the local MinIO's `TEST_S3_BUCKET`, emptied on start, whatever `S3_*` says, the same way SMTP goes to Mailpit. CI starts the same MinIO.
- **R2 smoke test:** `R2_SMOKE=1 pnpm test:r2-smoke` uses the bucket named by `S3_*` in `.env` and is skipped otherwise. It checks a PUT with a signed length, a refused wrong size and type, a refused second PUT, HEAD, a ranged GET, a presigned GET, a refused unsigned GET, and delete. It writes one object under `t/smoke/` and deletes it.

## Consequences
- No object exists without its row: the upload URL is returned only after the row commits, and a deleted row stays until its object is gone. A crash between a delete's commit and its object delete leaves work for the sweep, not an orphan.
- A browser upload to R2 needs a CORS rule on the bucket (deploy/README.md).
- A production bucket is provisioned outside the app, with its own token, encryption and lifecycle rules.
